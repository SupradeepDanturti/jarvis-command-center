# Laptop Jarvis voice

The planned expansion into a connected, personalized agent is recorded in [PERSONAL_ASSISTANT_PLAN.md](PERSONAL_ASSISTANT_PLAN.md). It includes the user's full-access Google service direction and editable memory/ongoing responsibilities. Those adapters and background assistant features are not implemented by the current voice worker described below.

## Scope

An optional laptop voice worker inside G16 Command Center, controlled from the existing HTTPS webpage. No Android app, separate assistant frontend, ElevenLabs, or local language model. The worker uses the laptop microphone and speakers; the Redmi remains a remote switch and status surface.

## Implemented flow

1. An approved loopback owner saves an OpenAI API key on More → Jarvis. Windows user-scoped DPAPI encrypts it in ignored `.state/private/voice/openai-key.dpapi`. No API response returns the key.
2. The user selects a laptop microphone from Jarvis or System & controls. Selection persists by a device-name/host identity rather than an unstable audio index. Stereo Mix and loopback inputs are excluded. Only 16 kHz mono-capable MME capture devices are offered. A refresh arrow enumerates inputs in a fresh short-lived process so newly connected devices are visible without restarting PortAudio inside an active worker.
3. An approved browser turns Jarvis on. The server starts an isolated, on-demand CPU worker. Disabled Jarvis holds no microphone or inference models. Closing the webpage leaves the worker running; server startup always begins off.
4. openWakeWord detects “Jarvis” locally using the pinned community `jarvis_v1.onnx` model at threshold 0.6. Say the name, pause briefly, then give the command. Hey Jarvis remains compatible. A command of up to ten seconds is collected in memory, ending after silence. The microphone closes before network requests and playback.
5. OpenAI `gpt-transcribe` transcribes the clip or a follow-up answer. The optional OpenAI Agents SDK runs a Jarvis Agent/Runner over Responses with `gpt-6-luna`, reasoning effort `none` and parallel tool calls enabled. Tools cover discovered app and Ambient catalogs, ID-based app launch, requested websites in Brave, media control, hardware status, dashboard screen/scene navigation and native web search.
6. The parent revalidates the action against its registry and current worker generation, and requires an unlocked Windows desktop. App/screen actions accept IDs; website opening separately validates a complete HTTP(S) URL for fixed Brave navigation. No executable paths, argument arrays, scripts or arbitrary commands are accepted from the model. Follow-up failures never retry completed physical actions.
7. Piper generates a synthetic Jarvis-style reply locally with `jgkawell/jarvis` medium. Playback opens an explicit speaker endpoint independently of the Windows default/headphones, with cancellation/lock checks between PCM chunks. Auto selects Realtek speakers; missing speakers fail visibly without falling back to headphones. After each reply, a configurable 15-second (default) or 30-second window accepts a conversational answer without another wake phrase. Off requires the wake phrase each turn. Silence or “thank you” returns to wake-word listening; Windows lock pauses recording.

## Interface

More → Jarvis provides microphone selection, on/off, fixed voice preview, status and saved conversation history with action results and clickable web sources. History is scrollable with earlier-page loading. Follow-up listening can be Off, 15 seconds or 30 seconds; changing this setting stops the current worker. Only the loopback owner can clear saved history, which also stops Jarvis. API key entry and deletion appear only on the approved localhost owner browser. System & controls also provides microphone and speaker dropdowns and an Open Jarvis shortcut.

Supported examples: open YouTube in Brave; open Discord/Steam; volume up/down, mute, previous/next, play-pause; CPU/RAM/GPU status. Play-pause is a toggle; volume sends one native Windows step per voice request. One physical PC control, one screen request and one hardware read may share an utterance when explicitly requested. General conversation uses the latest six saved exchanges as context. The system instructions request a calm, composed Jarvis-style manner with polished British phrasing, understated dry wit and sparing use of “sir”. Native Responses `web_search` (low search context) is available for explicit searches and current or uncertain facts. Up to five source links appear beside the saved answer; URLs are omitted from spoken output. Web content cannot authorize laptop actions.

## Saved introduction and persona context

`backend/agent/jarvis_intro.txt` holds the original spoken introduction. It describes the implemented app/website/screen/hardware capabilities with restrained British humour, without the reference transcript's fictional diagnostics, imported preferences or constant availability. The tagged system prompt adds persona/context guidance and examples for routine confirmations, scene requests, clarification and introduction playback. Ordinary answers retain their concise style and report actual tool results; urgent warnings remain direct and web/pasted text never authorizes actions.

`play_intro()` accepts no arguments and returns only the trusted local script, bounded to five hundred characters and four KiB on disk, whitespace-normalized and rejecting empty/control-character text. It is reread on every request. Exact recognized phrases such as “introduce yourself,” optional Jarvis/please punctuation, or “play your introduction/intro” route through the generation-gated parent dispatch without a conversation-model call. This still requires an enabled worker and OpenAI speech transcription. Quotes, negation, casual mentions and combined requests do not match this literal shortcut. Other explicit requests can select the SDK tool; a successful result overrides the model's improvised reply with the saved script, including after reply failure. The tool shares the physical-control slot and duplicate ledger, so parallel/extra rounds cannot replay it or add a second PC action.

The existing worker speaks the exact result through local Piper and the selected speaker, with the same cancellation/Windows-lock checks before synthesis, after synthesis and during playback. It sends the recognized request/script through the existing bounded private exchange history and status, without logging audio/transcripts, adding a database or enabling listening. There is no startup/autoplay, custom file/text/voice interface or extra browser endpoint. A missing/invalid script returns a tool failure instead of truncation or a model-generated replacement. Saved intro edits need no restart; installing the new command requires the normal backend reload and explicit re-enabling afterward.

## Completed-action reply style

Routine confirmations lead with the result, usually in three to twelve words, with composed British phrasing, occasional dry wit and sparing “sir”. The prompt waits for successful tool results before saying “YouTube opened in Brave”, “Steam opened”, “Clock selected” or a selected Ambient scene's name. It avoids intent narration and delayed “opening”/“requested” replies. No reference audio, new voice model or speech synthesis change is required.

App/website adapters return completed dispatch wording and navigation returns the selected destination, so the existing SDK reply-failure fallback uses the same style without replaying controls. These words acknowledge the supported dispatch/selection; they do not establish website loading, continued app operation, media state or browser display acknowledgment. Failures, timeouts, cancellation and unavailable controls never warrant a success confirmation. Existing widget setup, Rest and visible-browser delivery rules remain in force.

## Agents SDK runtime

`backend/agent/voice_agent.py` is imported only inside a conversation turn in the isolated enabled worker. It uses SDK `Agent`, `Runner`, `FunctionTool`, `WebSearchTool` and `OpenAIResponsesModel`; the existing synchronous OpenAI client still handles transcription. Each turn owns and closes an async API client on the fixed official endpoint, with zero transport/SDK retries, no server-side conversation/session IDs and `store=False`. The runner receives at most six saved exchanges and runs at most four model steps, allowing discovery before action and reply. Native hosted calls are limited to two per model step. Tracing is disabled globally and per run, sensitive trace data is disabled, and model/tool debug logging and the SDK logger are disabled before import/use. No extra SDK memory database, handoffs or MCP/shell capabilities are configured.

Parallel function tasks share a lock around the existing single parent pipe. Tool decisions can arrive in one batch; actual parent/Windows dispatch is serialized and results echo their unique request ID, so a late timeout reply cannot satisfy the next request and physical controls cannot race. Per-turn slots allow one physical control (app launch or media), one display request and one hardware read. A canonical call ledger reserves each operation before sending and reuses its result for duplicates across all SDK steps, including failures/timeouts; additional operations in a used slot are refused. Generation/lock/disable checks still run in the parent on every dispatch, and the worker checks cancellation before/after model calls and each tool. Reply failure reports all completed tool results without replay. The bounded existing history retains each result of a parallel batch in the exchange's action record.

## Discovered laptop apps

`list_apps()` reads the live parent `AppRegistry.voice_catalog()`: available saved shortcuts plus the same trusted Windows discovery used by the Settings picker, retaining its deduplication, local executable/package checks, exclusions and five-hundred-app bound. The twenty-five saved-shortcut limit does not limit voice choices. Results contain only IDs and names, without paths, arguments, package identities, icons or process details. The model receives these results for name matching; they are not saved as a full inventory in conversation history. Names are untrusted labels and cannot authorize actions. Discovery uses the existing thirty-second cache and has a separate read slot from Ambient discovery and hardware readings.

`launch_app(id)` accepts exactly one ID, with no caller paths/URLs/arguments. Its schema does not freeze a selected-app enum at worker startup: the SDK requires successful `list_apps` in this turn and membership in the returned IDs. The parent resolves only saved registrations or trusted detected records no older than two minutes, rechecks availability and launches through the existing shell-free executable or fixed AppsFolder adapter. It does not add a shortcut or persist inventory changes. Removing a shortcut affects browser launching but still permits voice discovery of a supported installed app. New/removed apps reach subsequent discovery without restarting the worker. Unknown, ambiguous or unavailable apps do not get guessed. The transcription hint also avoids a fixed app-name list.

Read-only app discovery runs outside the voice cancellation lock, with permission checks both before and after the read; disabling, changing worker generation or Windows lock rejects late results. The worker permits thirty seconds for the fixed bounded Windows reads, while all physical actions retain their five-second pipe wait. Launch refuses a busy inventory lock rather than waiting behind discovery under the voice cancellation gate. Apps share the one physical-control slot with media, and discovery does not consume that slot. Duplicates across SDK steps reuse their result. Existing browser launch and owner-only shortcut management endpoints remain unchanged.

## Requested websites in Brave

`open_website(url)` accepts exactly one HTTP or HTTPS URL for the user's explicitly requested website, without a saved app entry or app discovery. The agent may write a URL from a supplied address/known site and uses native search for an uncertain official address; ambiguity calls for clarification. Searching or reading a page alone does not authorize navigation, and untrusted web/tool text cannot request actions. The tagged prompt has a separate websites section, retaining concise spoken replies without reading URLs aloud.

The parent validator bounds the URL to two thousand forty-eight characters, rejects credentials, whitespace/control characters, backslashes, malformed hosts/ports and non-web schemes, and canonicalizes hostnames including IDNs/IPv6. It resolves only the trusted Brave alias and launches `[brave, '--new-tab', url]` without a shell. No model-supplied browser, arguments, headers, paths, OS protocols or backend fetches are accepted. Missing Brave and launch failures report generic errors with no fallback. URLs load in normal Brave; loading/redirects remain browser behavior. The action requests a tab, not confirmed loading, account interaction or installation. The same physical-control slot, duplicate ledger, cancellation, generation and Windows-lock gates apply. No dashboard browser endpoint is added; full tool URLs belong only to authorized bounded private conversation text/action records.

## Voice screen navigation

The Responses function `show_screen` accepts exactly one `screen` from a fixed enum: home, gaming (Live performance), games (library), apps, hardware, graphs, clock, focus, ambient, media, system, devices, rest, voice, widgets, weather or f1. The system instructions map “I want to play games” to the library and weather/forecast/AQI or next-race view questions to the corresponding widget. Specific facts beyond these local widgets or another named city can still use native search. Tool definitions live in `backend/agent/voice_actions.py`; `respond()` reads the UTF-8 `backend/agent/jarvis_prompt.txt` for each turn and replaces only `{now}` with the local date/time before calling the SDK runtime. The tagged prompt contains role, spoken style, actions, screen routing, search, security and examples, with sparing “sir” and spoken domain citations. Native source annotations still supply the saved clickable links. Editing this trusted local prompt affects the next turn without restarting an enabled worker; tool allowlists and parent permission checks remain enforced in code.

The parent revalidates the enum and live unlocked worker generation before publishing one in-memory request, with a random ID and ten-second deadline, through the existing authenticated voice status read. This is a delivery request, not a browser acknowledgment. Status removes pending requests on expiry, worker exit/disable, preview/error or lock; nothing persists or replays from history. No browser navigation mutation endpoint, arbitrary hash/URL/path or new physical control is added.

Each already connected, visible approved browser establishes its first status as a baseline, consumes each subsequent ID once, validates its destination/deadline/state and uses the existing page navigator. Reload, hiding, disconnection and unpairing reset that baseline. An open dialog blocks the request. Voice exits immersive presentation and applies the same two-minute manual hold as touch. Focus opens only its view; it does not start/reset the shared timer. Weather/F1 select only already-enabled views; missing consent or a missing weather city opens Optional widgets without changing opt-ins or location. Active Rest rejects navigation until the separately validated wake command exits it. Opening System/Devices/Jarvis confers no extra ownership permissions.

Natural-language routing is instructed through the existing conversational model, not a keyword trigger for casual mentions. Automated model-turn checks use mocked function choices; actual room recognition and cloud routing of paraphrases still require user acceptance.

### Discovered Ambient scenes

The trusted local `config/ambient-scenes.json` replaces the scene literal formerly in `frontend/screens.js`. `backend/ambient.py` validates bounded IDs/metadata, fixed local filename stems and supported movie types, and requires the movie and JPG poster to exist inside the local asset directory. Missing/corrupt/empty catalogs yield no options. Its generated same-origin `/static/ambient-scenes.js` supplies the Ambient buttons and background picker; it is public artwork metadata like existing static assets, never controls or private state. Labels are escaped for HTML, and an empty display catalog renders an unavailable message.

`list_ambient_scenes()` returns only available IDs, names and descriptions. `show_ambient(scene)` has a strict enum generated from that same catalog and is validated again in the parent. Voice schemas refresh every conversation turn, so catalog changes do not require a worker restart or edited name mappings. The SDK requires successful discovery in the current turn and a matching returned option before it dispatches selection; discovery has its own read slot, while selection shares the screen slot with `show_screen`. A named-scene request opens Ambient and selects that ID in one ephemeral navigation event. Generic Ambient keeps the current selection. Browsers revalidate against their loaded catalog and preserve/save scene selection without changing pause/reduced-motion settings or physical controls. Reload browsers after local catalog edits to load updated metadata. Existing generation, Rest, lock, expiry, once-only and visible/approved-browser guards also apply to scene selection.

## Iron Man interface and hardware warnings

- The voice screen uses a sourced transparent PNG Iron Man helmet stored locally with red/gold armor, cyan ring/scan animations, conversation history and the existing controls. Native phase changes drive animations. The graphics are status indicators, not measured audio levels.
- Home keeps the black-hole movie, telemetry, apps and media controls. One pointer-transparent HUD occupies its artwork stage; idle listening shows a compact armed indicator only on Home. Other screens hide idle/locked/error badges and show fresh starting/recording/transcribing/thinking/speaking/follow-up/preview/alerts activity. Widgets reserve an inline activity strip above a scrollable reading area; other screens use a compact header overlay, temporarily replacing the top bar. Immersive Clock/Ambient reserve heading/exit space below it. Labels/replies come from authenticated voice status; Home HUD readings come from live telemetry. No simulated diagnostics or invented progress appears. Off, stale/disconnected, hidden or unpaired pages hide the HUD and release activity space.
- Approved status polling runs on every screen while visible. A single HUD is moved between the Home stage, Widgets activity strip and shared overlay layer without losing current activity. Expired snapshots hide activity. Revocation/unpairing clears cached voice state. Reduced motion disables new animations; narrow/short landscape uses a compact overlay.
- An approved user can select a real speaker by enumerated device identity or Auto. Only speaker endpoints are listed; headphones/default sound mappers are excluded. Input and output identities persist independently. Preview uses this same output; other applications retain their Windows output.
- Local warning thresholds are CPU ≥90%, RAM ≥90% or GPU ≥70°C for three distinct fresh samples. Warnings combine eligible metrics, wait for unlocked idle wake listening, and are generated by Piper without cloud requests. All metrics share a 3600-second cooldown, persisted in private `alerts.json` across restarts; sustained high values may warn again after that hour. Alerts on/off is usable during a running session and cancels pending/current warning playback without stopping conversation listening.
- Warnings are marked as system alerts in the bounded private history and excluded from the six-conversation context sent to OpenAI. Missing/stale/invalid readings never generate an alert. Turning Jarvis off or locking Windows prevents warning playback; startup listening remains off.

## Private state and boundaries

- Runtime models and key live below the existing ACL-protected private directory. The installer fetches five ONNX/config artifacts and the wake model's MIT license over HTTPS, checks pinned SHA-256 digests and writes a local manifest. The wake model/license use immutable upstream revision `8bcd2f20bb7b76c351b2eff871fa1ce873fe9be2`. No model-training checkpoints or pickle weights are loaded.
- API audio and text requests go only through the server-side OpenAI SDK. No API key is in JavaScript, localStorage, URLs, logs or Git. No automatic cloud retries. Responses requests use `store=False`; native web search is performed by OpenAI, not an arbitrary laptop HTTP-fetch tool. API billing is required separately from ChatGPT subscriptions.
- Audio is not written to disk. Conversation text, timestamps, action results and safe source links persist in `.state/private/voice/history.sqlite3`, retaining the latest 500 exchanges across restarts. Approved browsers can read history; only the direct-loopback owner can clear it. Each cloud turn includes at most the latest six exchanges. Disabling clears the transient status but preserves saved history. Synthetic previews generated during development are ignored test artifacts.
- Native recording is opt-in through the on switch. An approved tablet may start/stop the laptop microphone, like other authorized laptop controls. The wake word does not identify the speaker; nearby speech or media can trigger it.
- Stopping invalidates the worker generation, signals cancellation, then terminates it if necessary. A lost parent pipe ends the child. Late cloud results cannot dispatch actions after disable; locking also prevents dispatch.
- Key storage does not validate API access or billing. Cloud error messages are generic and never expose exception request contents.

## Dependencies and reuse

Install optional dependencies with `requirements-voice.txt`, then run `scripts/install-voice.py`. The existing non-voice dashboard remains usable without these dependencies.

Use Piper through its published Python API and openWakeWord through its inference API. The G16 adapter, supervisor, action boundary and webpage are original project code. We do not copy the Dix01/JARVIS assistant or its frontend.

- [Piper](https://github.com/OHF-Voice/piper1-gpl): GPL-3.0 engine dependency.
- [Jarvis model](https://huggingface.co/jgkawell/jarvis): published MIT model; a synthetic approximation, not a verified exact movie voice.
- [openWakeWord](https://github.com/dscripka/openWakeWord): Apache-2.0 code; bundled pretrained wake models CC BY-NC-SA 4.0. Current installation is for personal use.
- [Jarvis wake model](https://github.com/fwartner/home-assistant-wakewords-collection/tree/8bcd2f20bb7b76c351b2eff871fa1ce873fe9be2/en/jarvis): community model targets Jarvis and Hey Jarvis. The collection is MIT, copyright 2023 Florian Wartner; its license is installed beside the model. The publisher reports sensitivity/false-activation tradeoffs; this desk's error rate is unmeasured. Synthetic test clips do not establish room accuracy.
- [OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling) and [file transcription](https://developers.openai.com/api/docs/guides/speech-to-text) and [native web search](https://developers.openai.com/api/docs/guides/tools-web-search).

A complete mocked worker turn verifies “Which app?” → “Steam” without a second wake detection. Native checks load the actual ONNX voice and wake model and synthesize speech without cloud access. Browser checks verify setup/navigation and dropdowns using a QA credential without changing the user's voice configuration.

## Focus completion announcements

The laptop-owned focus timer has an independent announcements preference, off by default. A completed phase can queue one fixed local phrase for an already-enabled Jarvis worker. Delivery waits for Listening, expires after 60 seconds and requires the same worker generation and unlocked desktop. Reset, skip, starting the next phase, preference changes, disabling Jarvis or locking cancel pending/late speech. The worker rechecks cancellation after synthesis and while playing audio. Missed/overdue recovery does not replay announcements.

These reminders use the selected local speaker and Piper voice without wake capture, STT, OpenAI requests, follow-up capture, transcripts or conversation-history entries. They do not change the hardware-alert switch/thresholds, turn listening on, or add voice action capabilities.

## Explicitly scheduled alarm speech

[Rest & alarms](REST_ALARM_SPEC.md) has separate per-alarm speech consent. Its isolated local Piper/speaker process opens no microphone, OpenAI client, credentials, wake detector or tools and creates no history. A chime precedes “Sir, it's time to {label}.” It can play with Windows locked and conversational Jarvis off, without unlocking or enabling listening. Preview and ringing stop conversational Jarvis; re-enable listening explicitly afterward. Entering Rest keeps an already-enabled Jarvis running. Speech repeats every 30 seconds for at most ten minutes; snooze/dismiss/cancel/replacement/shutdown stop it with cancellation checks after synthesis and between chunks. A fixed ten-second preview never changes the alarm or monitors. Missing installed voice dependencies permit visual-only alarms, and no API key is required. Existing conversational and Focus lock checks still apply to those workers.

## Literal voice Rest entry and wake

“Jarvis, enter rest mode” enters Rest and preserves any alarm. Capture closes before acknowledgment and monitor preparation, then resumes wake detection using the same loaded models. Button entry also preserves an already-enabled worker; neither route enables a disabled microphone. “Jarvis, wake up” restores the retained monitor handles and shared tablet page without changing the alarm, speaks after the power action and resumes ordinary wake listening. Say Jarvis, pause briefly, then say the command. The old Hey Jarvis phrase remains compatible.

Both fixed transcripts, optional Jarvis prefix/suffix, wake-phrase punctuation and optional please are matched outside the conversational model; no Rest/wake tool is supplied to the cloud. The parent validates each phrase and binds actions to the live unlocked worker generation with a 25-second deadline. Entry still uses device-bound preparation/confirmation. Native queue and per-monitor cancellation/deadline checks reject late actions after disable, lock, worker replacement or expiry. Successful actions and fixed failure reasons go only to bounded private history. Windows lock pauses listening, startup keeps it off, and no voice unlock or actual-system-sleep wake is added. Normal STT still requires the saved key and internet.
