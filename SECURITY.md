# Approved device access

The HTTPS dashboard serves telemetry and controls only to approved browsers. The login shell and health endpoint remain public; unauthenticated devices cannot read hardware data, launch apps, send media controls, or open the telemetry WebSocket. This is an application allowlist, not a claim that other computers cannot reach the network port.

## Add your Redmi

1. Copy **G16 Dashboard CA.cer** from the laptop's Downloads folder to the tablet using a trusted transfer (such as USB), or download it at `http://LAPTOP_IP:18760`. With an HTTP download, compare the installed certificate's actual SHA-256 fingerprint with the trusted laptop connection file before using it.
2. In Android settings, install it as a **CA certificate**. Search settings for “CA certificate”; menus vary by Android/HyperOS version. If opening the downloaded file shows “Install CA certificates in Settings,” close that message and install through Settings instead. Install this public certificate, never a private key.
3. Open the `https://` tablet address in **G16 Command Center.txt**. Certificate validation must succeed; do not bypass browser security warnings.
4. Name the browser, then tap **Request approval**. Its fingerprint appears while it waits.
5. On the laptop, open **https://localhost:18761**. For first-time laptop access, enter the setup/recovery code from the connection text file.
6. Open **More → Device access → Approved devices** (`https://localhost:18761/#devices`), match the tablet's displayed name and fingerprint, then approve it. This list is also available on System.

The browser now reconnects without a code, including after laptop/server restarts. Approval lasts up to 180 days. Use the same browser/profile and address; clearing cookies, using a different browser, or changing the hostname/IP requires fresh approval. A router DHCP reservation can keep the Wi-Fi address stable.

## Remove a device

Use **More → Device access → Approved devices → Revoke access** on the laptop at localhost. Revocation immediately denies new requests and closes its live WebSocket within roughly one second. Unpairing from the device revokes that browser too. Each browser has its own credential, so revoking one does not disconnect the others.

## Boundaries

- Device approvals and revocations require an approved owner browser **and** a direct loopback connection. They cannot be performed by the tablet or through forwarded-client headers. The background server disables proxy-header trust.
- Knowing the recovery code does not authorize a remote device; it creates only a pending request that still needs laptop approval. Remote devices can also request approval without a code.
- Pending requests expire after ten minutes and are limited per address and globally. Unknown/expired/revoked credentials are denied.
- A random 256-bit browser credential is stored in an HttpOnly, SameSite=Strict, Secure cookie over HTTPS. The SQLite registry stores only its SHA-256 hash, device metadata, and approval status. Credentials are not URL parameters or localStorage values.
- The device SQLite database stores access metadata. Jarvis has a separate private conversation SQLite file as described below. Server logs remain rotating files, and telemetry history remains in memory.
- Approved browsers can report only their own display dimensions, orientation, scale and fullscreen state over same-origin HTTPS. Device identity comes from the authenticated cookie; the request cannot select another device. Reports contain no credentials or hardware identifiers, are bounded to 128 current reports, expire from memory after five minutes, and are removed on revocation/logout. Only a direct-loopback owner can read device reports. These are browser-reported layout diagnostics, not proof of physical hardware identity.
- The game catalog, local game artwork, library refresh, and game launch require approved browser authentication. Refresh/launch also enforce same-origin requests. Launch requests contain only a detected ID; paths, URLs, arguments, and artwork paths come from trusted laptop records. Steam/Epic URI identifiers are generated/encoded by the server; other games use executable argument arrays without a shell.
- Ambient media and app logos are public static assets without credentials or personal game artwork. Scene/time-format preferences use localStorage; authentication credentials remain exclusively in HttpOnly cookies.
- This recognizes browser credentials, not immutable physical hardware. A copied/stolen browser profile can impersonate it. Keep the laptop/tablet locked and revoke a device if lost.
- Passkeys are not implemented in this release. WebAuthn needs a supported HTTPS origin and stable domain. Synced passkeys can also be available on multiple devices; they do not inherently enforce a physical-device allowlist.
- Bluetooth transport is not implemented. Pairing Bluetooth by itself does not authenticate HTTP or WebSocket requests.

## Personal assistant access

All `/api/assistant/*` routes require HTTPS plus an approved owner credential and a direct-loopback peer. Ordinary approved displays cannot read account identity, profile or calendar data, including by spoofing forwarded-client headers. Mutations and the on-demand calendar read require same-origin requests. Input-validation failures omit submitted data, including client JSON. Owner revocation is rechecked before delivering a calendar response and while consent is pending.

Google installed-client values and refresh tokens are DPAPI-encrypted in ignored `.state/private/voice/google.dpapi`, under the existing private-state ACL; access tokens stay in memory. OAuth uses an external browser, PKCE, single-use state and a five-minute receiver bound to `127.0.0.1` on an ephemeral port, independent from dashboard/setup listeners. The receiver has no dashboard endpoints and logs no request paths/codes. Provider requests use fixed HTTPS Google endpoints with redirects/proxy inheritance disabled. No credentials enter the model, browser storage, status responses or Git.

The account-access switch is off on startup and separate from microphone listening. Stop/disconnect, account changes, lock and owner revocation invalidate pending access/results. The owner-only editable briefing profile is one bounded row in the existing private voice SQLite file; forgetting preferences and clearing conversations are separate operations. Dashboard Calendar/Sheets payloads are transient. Owner opt-in personal-context consent permits selected facts/preferences and requested provider results to reach OpenAI for voice answers. Personal replies are marked separately in bounded history and are visible only to the direct-loopback HTTPS owner; they are excluded from model context while personal consent/access is off. They do not enter shared telemetry. Facts/proposals are bounded private SQLite rows; explicit current-transcript remember requests save directly, while inferred facts wait for owner approval. Edits and clearing stop the voice worker, invalidate its context generation and clear previews. Sheets tools use account-bound registered ranges; a same-origin owner must apply a five-minute single-use RAW preview. No automatic write retries or arbitrary HTTP/Drive/shell tools exist. Credentials remain DPAPI-protected; the SQLite database itself is ACL-protected rather than DPAPI-encrypted. See [tools and memory](spec/ASSISTANT_TOOLS_MEMORY.md) for retention, voice audibility and uncertain write outcomes. Local disconnect removes local tokens; revoking the provider's grant remains an explicit Google-account action. See [the foundation record](spec/ASSISTANT_FOUNDATION.md) for setup, scope limits and unperformed live-account acceptance.

## Laptop voice access

Jarvis starts disabled and acquires the laptop microphone only after an approved browser enables it. Approved browsers can read its saved conversation history and change the capture input, explicit speaker output, follow-up setting or alerts switch. Only a direct-loopback owner can delete history; deletion stops the worker and clears its conversation context. Stereo Mix/loopback inputs are excluded. Closing the browser leaves the worker running; turning it off releases the microphone and inference process. Windows lock pauses listening and prevents action dispatch; a server restart starts it off.

Only a direct-loopback owner can save/delete the OpenAI API key. It is encrypted with user-scoped Windows DPAPI beneath the existing ACL-protected private state, never returned by an API, and never stored in JavaScript/localStorage. The password field clears after submission. API exceptions are reduced to generic messages; recordings/transcripts/keys are not logged. The key is passed to the child through Windows process initialization memory, never as a shell argument or environment variable. OpenAI requests use the fixed official HTTPS API endpoint.

Local wake detection is not speaker authentication. After activation, a short clip is uploaded for transcription, followed by command text for interpretation. Audio remains in memory and is discarded. By default, after a spoken reply the microphone accepts a follow-up for 15 seconds without a wake phrase; this can be set to 30 seconds or Off. Text, timestamps, action results and safe citation links persist in the ACL-protected, ignored `voice/history.sqlite3`, capped at 500 exchanges. Disabling preserves these records; explicit owner deletion uses SQLite secure deletion. The latest six exchanges are included in OpenAI turns, including after restart; Responses requests set `store=False`. Model-selected actions undergo exact argument validation against trusted app/media records or the separate website URL validator. No arbitrary executable/path/argument/shell interface is provided. Action dispatch is refused after worker cancellation or Windows lock; completed actions are never retried because a reply request fails.

Native Responses web search is available for current/uncertain information or explicit searches. Web content is treated as untrusted data in the system instructions and cannot authorize laptop actions. Citations are bounded to five HTTP(S) links without embedded credentials and rendered as escaped, clickable links alongside the reply; URLs are not spoken. The laptop provides no arbitrary network-fetch tool.

`open_website(url)` is a narrowly scoped user-authorized browser-navigation tool. It accepts exactly one bounded complete HTTP(S) URL, canonicalizes the hostname (including IDN/IPv6) and port, and rejects missing/malformed hosts, credentials, whitespace/control characters, backslashes and non-web schemes. It resolves the fixed local Brave executable and passes a fixed `--new-tab` plus the URL as separate arguments with `shell=False`; no caller browser, executable, headers, argument arrays, file access or parent network-fetch capability is exposed. Website opening shares the physical-action budget and duplicate ledger with app/media controls, and requires the live unlocked enabled worker generation. It never confirms loading or interacts with accounts/forms/downloads. Website names or search links may identify an explicitly requested destination; search/page/tool instructions cannot authorize opening it. Browser HTTP endpoints, setup-only HTTP, CSP, credentials and approval boundaries remain unchanged. Opening runs in the user's normal Brave profile, which handles website loading and its own redirects; no dashboard credentials are forwarded by the backend.

The optional OpenAI Agents SDK lives only in the isolated voice process. Tracing is disabled globally and per run, sensitive trace data and SDK model/tool debug output are disabled, and its logger is disabled. Responses remain `store=False`, with no remote conversation/session IDs and no automatic retries. Parallel tool selection is enabled, but dispatch through the parent pipe is serialized, bounded to one physical PC control, one screen request and one hardware read per turn. Duplicate calls reuse the first result, including timeouts/failures, across all bounded SDK steps; cancellation/lock/generation are rechecked before every dispatch. Parallel results use the existing bounded private history, with no separate SDK database.

Screen navigation accepts only fixed dashboard IDs. Requests are ephemeral, authenticated status data with a ten-second expiry and once-only consumption by already connected visible browsers; first snapshots, reload/hide/reconnect and revocation cannot replay them. Opening owner-management pages does not authorize their controls. Weather/F1 preserve browser opt-in and selected location, and missing setup opens settings. Active Rest blocks navigation rather than waking monitors. The trusted local `backend/agent/jarvis_prompt.txt` is read each turn; prompt changes cannot expand the separately validated parent tool registry beyond its fixed controls and scoped HTTP(S) website opener.

Ambient scene selection reads a bounded trusted local catalog shared with the display. Scene IDs are validated against existing local movie/poster entries, refreshed for voice schemas each turn and revalidated by the parent/browser. The model receives only IDs/names/descriptions, must discover the available choices before selection, and submits one ID rather than paths, media URLs or arguments. Catalog captions are escaped, and the public generated scene script contains only existing artwork metadata. Scene selection uses the existing ephemeral authenticated navigation request and preserves motion consent; it grants no new physical action or owner-management capability.

Spoken hardware warnings are opt-in with the Jarvis service, controlled by the Alerts on/off switch, and operate only on fresh local CPU/RAM/GPU readings. Three high readings are required; a global one-hour cooldown is saved in private ignored `voice/alerts.json`. Warnings use local Piper without cloud calls and are excluded from conversation context. Disabling alerts signals the worker to cancel pending/current warning playback; stop/lock checks also apply between output chunks. Speaker selection accepts only a real enumerated speaker ID, never a browser-supplied device index/path; no default/headphone fallback is used. Home activity/replies are shown only with approved, fresh voice status and live connectivity and are cleared on unpairing.

Optional runtime models are downloaded from fixed publisher URLs, checked against pinned SHA-256 hashes, and stored in private ignored state. Existing dashboard pairing, TLS and setup-only HTTP boundaries are unchanged. See [JARVIS_SPEC.md](spec/JARVIS_SPEC.md) for component licenses and remaining physical validation.

## Local certificate and private files

`scripts/setup-https.ps1` creates a private local CA and server certificate, installs the public CA into the current Windows user's trust store, and exports only the public `.cer` file to Desktop/Downloads. Android trust requires the one-time installation above. The certificate identifies localhost and the laptop's current network addresses.

Private state is in ignored `.state/private/`, with Windows ACLs limited to the current account, SYSTEM and administrators. The CA signing key is protected with Windows DPAPI for this user. The server key remains in the protected directory for unattended HTTPS startup. Never export keys or copy the private state into a public/shared location.

The server refreshes its leaf certificate when network addresses change or renewal is needed. Clients still need to use an address matching its certificate; old cookies do not migrate to a new hostname/IP. Certificate trust persists across normal restarts. If the CA needs replacement, device trust must be renewed explicitly.

The background process also serves a setup-only HTTP listener on port 18760, containing public certificate download and instructions. It has no authentication credentials, hardware readings or Windows controls. An HTTP download can be substituted by a network attacker, so verify the installed CA fingerprint against the laptop's trusted file, or transfer the certificate over USB.

To remove Windows trust later, locate **G16 Command Center Local CA** in the current user's Trusted Root Certification Authorities and remove only that certificate. Remove the corresponding installed CA on Android too. Do not delete private state while the server is running.

References: [WebAuthn](https://developer.mozilla.org/en-US/docs/Web/API/Web_Authentication_API), [browser cookies](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie), [Web Bluetooth](https://developer.mozilla.org/en-US/docs/Web/API/Web_Bluetooth_API).

## Media, focus and optional sensor data

Media snapshots/artwork and focus state require approved HTTPS access. Media controls and timer changes also require the dashboard origin; session controls validate opaque current-session and track revisions before dispatch. Seeking accepts only a finite in-track position. Artwork is a bounded, validated PNG/JPEG/WebP from the selected Windows session, held in memory and served under an opaque revision, with no remote URL/path input or artwork history. Track text is rendered as text. Approved browsers can see the current track; it is not recorded in logs or the device database.

Timer state/settings are held in ignored `.state/private/focus.json`; browsers receive shared state with a revision to prevent conflicting changes. Fixed local completion phrases are bounded, expire after 60 seconds, wait for an idle Jarvis worker, and are cancelled on replacement/reset/skip, lock or disable. They do not enable listening, invoke an OpenAI request or enter conversation history.

Foreground activity reads only the current process executable and matches trusted game records. It sends a bounded matched game ID/name and observation timestamp; it does not capture window titles, command lines or screenshots. Display preferences are harmless browser-local settings.

Optional HWiNFO reads a fixed named mapping with read-only access under the provider mutex. Header/version/offset/count/size/timestamp/unit checks reject incompatible or stale data. Sensor selection/inventory is direct-loopback-owner-only, with same-origin writes, and persists in ignored `.state/private/thermal.json`. No browser paths, provider names, memory addresses or hardware-write commands are accepted. Fixtures never become live readings. Existing setup-only HTTP, approvals, CA trust and voice-key protections remain unchanged.

## Rest mode and scheduled alarm

Alarm reads require approved HTTPS/WSS; writes additionally require the dashboard origin. Strict revisions prevent conflicting changes. Rest entry uses a single-use, device-bound 30-second nonce after browser confirmation. A fixed native adapter holds temporary display/system/process execution requests and sends only DDC/CI monitor-power Off/On values to locally discovered, capability-checked monitors. No system-sleep broadcast, arbitrary hardware code/value, shell, URL, path, input injection, unlock or power-policy editor is exposed.

One shared alarm, bounded printable label and revision are saved privately in ignored `.state/private/alarms.json`. Persist-before-dispatch, silent missed recovery, clock-change pause and finite repetition prevent unbounded or replayed alarms. Browser labels render as text. The optional alarm-only process loads local Piper/speaker dependencies only for explicitly requested preview or speech, without microphone, cloud, credentials, model tools, history or audio/label logging. An explicitly armed alarm can speak while Windows is locked or conversational Jarvis is off; this separate consent never enables listening. Cancel, snooze, dismiss, replacement and shutdown cancel audio. Existing conversational Jarvis/Focus lock restrictions remain unchanged. Closing or unpairing a browser does not cancel a laptop-owned alarm; cancel it explicitly from an approved browser.

An enabled, unlocked Jarvis worker may request Rest entry with the literal “enter rest mode” transcript or restore this dashboard's monitors with “wake up.” Both phrases are checked in worker and parent and cannot be issued through model tools or web search. Capture closes during actions/speech, then wake detection resumes with the same loaded worker. Button entry also preserves an already-enabled Jarvis session; entering Rest never enables a disabled microphone. A voice-generation-bound nonce/revision protects entry, and both fixed actions have finite deadlines and live-worker cancellation checks before/between queued native writes. Disable, lock, replacement and expiry cancel late actions. Wake uses only this adapter's retained off handles, exits the shared dim screen and preserves the alarm; it never unlocks Windows or wakes an actually suspended system. Authorized command/results go only to bounded private voice history. Startup still leaves listening off; Windows lock pauses capture. Alarm ringing/preview still stop conversational Jarvis to prevent overlapping alarm audio.

## Requested local introduction

`play_intro` reads only the fixed trusted `backend/jarvis_intro.txt`, with no caller text/path/URL/voice arguments. Empty, oversized or control-character scripts fail. The introduction is bounded to the existing five-hundred-character speech/history limit and is reloaded per request. Literal recognized introduction commands skip conversational inference but still dispatch through the live enabled/unlocked worker generation; SDK paraphrases share the physical-action budget and duplicate ledger and speak the same saved script rather than model improvisation. Existing selected-speaker playback cancels on disable/lock; nothing starts automatically or enables listening. The recognized request and spoken script use only the existing bounded private history. Persona examples in the prompt are style/context, never permission to invent readings, diagnostics, imported preferences, alarms or fictional capabilities.

## Detected app shortcuts

Reading detected-app inventory and adding/removing shortcuts require the approved direct-loopback owner; writes additionally require the dashboard origin. Detection reads fixed Windows App Paths and Start Menu locations for drive-qualified local executables, plus installed package manifests matched to registered Start-menu application identities. It excludes shells/interpreters/installers, arbitrary shortcut arguments, scripts, URLs and network shares. Packaged launches use only the fixed AppsFolder prefix plus the validated server-discovered identity; callers cannot submit identities, paths or launch arguments. The fixed bounded shortcut-reader command never executes shortcuts or incorporates browser input.

The browser receives IDs/names only and submits a detected ID. Registration rechecks file availability, rejects expired/unknown/duplicate IDs, and enforces 25 total apps under a shared lock. The full selected list is atomically persisted in ignored ACL-protected `.state/private/apps.json`; a failed save leaves the active list unchanged. Initial local configuration remains intact. Approved tablets can launch only registered IDs, with no arbitrary path/URL/argument API. Removing a registration denies subsequent browser launch by that ID. Shared catalog updates reach open tablets through the existing 15-second polling.

An enabled Jarvis has separate read-only `list_apps` discovery covering available saved shortcuts and the same bounded Windows inventory (up to 500 detected apps) as the Settings picker. Only IDs/names are returned to the model. The SDK requires successful discovery in the current turn and a matching returned ID before `launch_app`; the parent revalidates the ID against trusted saved records or discovery no older than 120 seconds, and rechecks local executable/package availability. Detected apps never receive caller-supplied arguments. Opening an unselected app does not register it, persist it, or expose an expanded browser endpoint. Removing a shortcut does not prevent voice discovery of the still-installed app. Shell/interpreter/installer and shortcut-argument filters remain in discovery. Slow read-only enumeration releases the voice cancellation lock and rechecks generation/phase/disable/Windows lock before delivering its result; physical launch refuses a busy inventory lock and keeps the existing short tool deadline. App names are untrusted labels, never authority for actions. App discovery uses its own read slot, while all app launches share the single physical-control slot with media. Normal turns do not store full inventories in private conversation history or logs.

The Jarvis HUD now uses approved fresh voice status on every visible screen. Hidden, stale/disconnected, expired and unpaired views suppress activity; unpairing clears private cached voice state. Setup-only HTTP, browser approvals, credentials and CA trust are unchanged.

Added-app logos are approved-only PNG responses selected by a saved app ID. Executable icons are extracted locally with Windows Shell/GDI; package logos must remain inside the registered installation directory, be bounded PNG files, and have bounded dimensions. No browser file path or remote image URL is accepted. Missing icons use a generic local glyph, and removing a shortcut removes access to its cached icon.


## Optional read-only widget feeds

Widget settings are harmless browser-local preferences, off by default. City search requires an explicit submission; Weather sends rounded selected-city coordinates only while viewed. No GPS permission, credentials or feed history are stored in browser preferences. The selected city/search text reaches Open-Meteo through the PC, whose public network address is visible to providers.

All feed reads require approved HTTPS access. City search and coordinate requests require the dashboard origin and strict bounded inputs. Fixed HTTPS Open-Meteo/Jolpica endpoints accept no browser URLs, hosts, keys, paths, arguments or commands. The PC never forwards browser credentials, follows provider redirects, uses public CORS proxies or loads third-party frontend code. CSP remains same-origin; the setup-only HTTP listener gains no endpoints.

Provider work is limited to four pending fetches, 30 new calls per minute, a 512 KiB reply cap and finite deadlines. Identical fetches share work; a 32-entry memory cache bounds retained results. Failures cool down and expose only generic states; provider exceptions/query strings are not logged. Cached failures are visibly stale and expire. Numeric/time validation and escaped text rendering reject or contain malformed upstream data. No remote images/markup/provider URLs are rendered or dispatched; widgets cannot invoke voice/control tools.

Browser requests stop on leaving/hiding, disabling, Rest or unpairing, and late responses cannot repaint a replaced view. Already-started read-only PC fetches may finish into the bounded shared cache for other approved browsers; server shutdown cancels pending tasks and clears it. Existing owner management, approvals, cookies, CA trust, private-state protection and listening-off startup behavior remain intact. See [WIDGETS_SPEC.md](spec/WIDGETS_SPEC.md).
